## 台账与快照的边界（v3.58.20，P1-A）

- `cashflowStore` 管**每月一次的快照**，`debtStore` 管**逐笔台账** —— 改一笔台账只刷新台账，不触发全页重拉。
- 列表接口返回**裸数组**，`debtStore` 直接按数组赋值；若被全局分页包成 `{count, results}`，这里会得到 `undefined` 而**静默显示为空**。
- 账龄桶的标签与顺序**由后端下发**（`summary.aging`），前端只做渲染与着色，不重定义天数阈值。
- 新面板的金额/人名/利率全部走 `shared/utils/privacy` 的统一实现，**不内联 `privacyMode ? '***' : x`**。
- 接口失败的文案一律走 `shared/utils/apiError` 的 `apiErrorText()`（**唯一实现**，v3.60.18）。
  🔴 **5xx 不许把后端原文读给用户看**：`DEBUG=True` 下 500 回的是一整页 HTML Traceback（实测 20KB+），
  塞进提示条不只是「让用户读栈」—— 那坨文本会把提示条撑满整屏、**盖住后面的按钮**（实测点不动）。
  4xx（「会变成负数」这类**用户能改的**）必须原样透出，但统一截断到 120 字。

## 新科目体系与旧表的边界（v3.58.21，P1-B）

`assetStore` 一面，`cashflowStore` 另一面 —— **两套并行，不自动迁移**：

| | `cashflowStore`（旧表 `wealth_cash_flow`） | `assetStore`（新三张 managed 表） |
|---|---|---|
| 科目 | 8 个物理列，加科目要改外部表 | 科目主数据表，加科目只是插一行 |
| 分类 | 无 | 流动性 / 投资性 / 应收 / 自用 |
| 明细 | 一行装 8 个科目 | 一科目一明细行 |
| 汇总 | `total` / `realnum` | 含自用与可变现两个口径 |

- **列表接口一律返回裸数组**（`asset/accounts/`、`asset/snapshots/`）：被全局分页包成 `{count, results}`
  时前端按数组消费会拿到 `undefined` 而**静默显示为空**。快照用 `limit`（最近 N 期）而非分页 ——
  月度数据上分页器只是噪声。
- **汇总恒等式一律由后端算**，前端不做除法、不重算净 worth；弹窗里的「实时预览」只是把同一套
  口径在输入态复算一遍供心算校验。
- **脱敏边界**：列表行、应收差额提示等**已落库数据的呈现**一律掩码；
  弹窗里的**实时预览**（由输入派生）**刻意不掩** —— 边录边掩等于让人闭着眼记账。
- 科目主数据面板**不接脱敏**：科目名与机构名都不是隐私项，而金额根本不在主数据里。别顺手加掩码。
- ⚠️ 旧「对账」按钮（`GET /asset/snapshots/compare/`）**已于 v3.60.7 随接口一起下线** ——
  回填后两边同源，比对退化成恒等式。前端**零调用方**，**别照这句把它加回来**。

## 分类规则与账单的边界（v3.58.22，P1-C）

`classifyStore` 是第四把尺子 —— 它量的**不是金额，是性质**：同样的流水，
换个规则就换个结论。这与前面三个 store 的差别必须在写代码时记住：

| | `cashflowStore` | `debtStore` | `assetStore` | `classifyStore` |
|---|---|---|---|---|
| 度量对象 | 月度资产快照 | 逐笔负债/应收 | 科目与科目快照 | **账单的性质标签** |
| 数据来源 | 旧外部表 | 两张 managed 表 | 三张 managed 表 | 一张规则表 + 实时算 |
| 写入影响 | 只影响本期 | 只影响本笔 | 只影响本期 | **影响全部历史期的报表** |

- **改规则会让往期数字一起变**，这是刻意的（金额是历史事实、分类是当前视角）。
  所以 `saveRule` / `removeRule` / `toggleRule` / `seedRules` 之后必须重拉
  `summary` 与 `unclassified`，否则界面显示的是改规则之前的世界。
- 保存前先调 `previewRule`（不写库）。看影响面要看 `changed_count` 而不是
  `matched_count` —— 低优先级的候选规则可能命中一大片却一条都改不动。
- 预览结果**刻意不进 store**：它跟着弹窗走，存起来会在下次打开表单时残留，
  看着像已生效。
- 三维度覆盖率的分母**各不相同**（收入总额 / 支出总额 / 收支合计），
  所以三个百分比之间**不可比较**，UI 上也分开呈现、各自标注分母。

### 这一页的脱敏判据

| 内容 | 是否掩码 | 理由 |
|---|---|---|
| 金额 | ✅ 一律走 `formatAmount`（自带掩码） | 由已落库账单算出的展示值 |
| 商户名 | ✅ `maskText` | 实测商户取值含地名（福州 / 宁德 / 杭城），属「地点/文本」 |
| 规则匹配值（当 `rule_field=merchant`） | ✅ 同上 | 与商户同类 |
| 分类 / 子分类名 | ❌ 不掩 | 是使用者自建的分类 taxonomy（食品酒水 / 房租 / 学习进修），非身份信息；掩掉后认不出该给哪类建规则，属「掩码用力过猛」 |
| 弹窗内的输入与预览 | ❌ 不掩 | 输入态（见 §隐私 v3.58.18 覆盖范围判据） |

## 比率体系：阈值只在后端有一份（v3.58.23，P2-A）

`ratioStore` 是第五把尺子，也是唯一一把**自己不定义任何刻度**的尺子。

🔴 **一条铁律：`ratioStore` 与 `ratio/` 下的组件里不允许出现任何阈值数字。**

判断线（「多少算充足 / 多少算高危」）只在后端 `constants.RATIO_BANDS` 存在一份，
随接口以 `bands` 下发：

| 谁 | 负责什么 |
|---|---|
| 后端 `RATIO_BANDS` | 「value 落在哪一档」—— 唯一真源 |
| 后端 `grade_ratio` | 把 value 判成 `good / warn / danger / normal` + 中文标签 |
| 前端 `levelColor` / `levelClass` | **只**回答「这个级别画什么颜色」（`utils/ratioLevel.ts`，与健康指标卡共用） |
| 前端 `RatioScaleBar` | **只**按 `bands` 画档位宽度，不参与判档 |

于是「调阈值」永远只是后端改一个常量、前端零改动。
曾经写在 `HealthMetrics.vue` 里的 `months >= target / 2`、`ratio > 30 ? 'warn' : ...`
都是这套规则的反面教材 —— 那种写法下改后端常量不会改变界面结论。

### 三条必须记住的口径

1. **`value === null` 不是 0。** 算不出来（缺快照 / 支出为 0 / 标注填写率不足）
   一律 `available=false` + `value=null` + `reason` + 补救 `hint`。
   0 是一个**结论**（「你有 0 个月应急金」），拿 0 冒充没数据会显示成最坏结论。
2. **趋势的缺月要画成断点。** `series[k][i].available=false` 表示该月算不出，
   sparkline 必须断开 —— 若当 0 补点，会画出「这个月净值没变化」的假平线。
3. **比率不是金额，不套金额掩码。** 趋势上的百分比/月数一律不掩
   （与 `goals.progress_percentage` 同一条判据：百分比非隐私项）；
   但卡片的**分子/分母与资产位置**是金额，一律 `formatSignedAmount`（自带掩码）。

### 数据源与档位的几个易错点

- **资产来源整条切换**（有新科目快照 → 整体用新体系，否则整体回落旧表），
  **不逐月混合** —— 逐月混会让一条趋势线中间悄悄换过口径，图上完全看不出。
  `source` 与 `carried` 必须在界面上显式展示。
- 卡片上的**活期占比 / 负债率 / 公积金占比**与比率面板**共用同一张判定线总表**，
  但**不进比率面板**（`RATIO_ORDER` 是面板的唯一出口清单）。
  三条比对：`liquidity_ratio` 两端都不好故 `neutral`；`provident_fund_ratio`
  高档位是 `warn` 而非 `danger`（公积金不是坏资产，只是流动性差）。
- 期初对照弹窗的「变化」列**刻意不着色** —— 按符号上色会把「借款增加」画成绿色。

## 统计口径要看得见：气泡 + PERT 分母（v3.58.24）

「这个数字怎么算出来的」以前只存在于后端常量和代码注释里 —— 使用者看见
`16.2` 这个数，无从判断它可不可信。现在它是**接口下发的界面元素**：

| 层 | 内容 |
|---|---|
| 后端 `RATIO_BANDS[key]['note']` | 口径说明（`list[str]`，逐行）—— 唯一真源 |
| 后端 `/wealth/ratios/meta/` | 九项 `{formula, note, bands, unit, target}` 裸数组 |
| 前端 `MetricTooltip.vue` | ⓘ 悬浮气泡：公式 → 口径要点 → 判定分界（不写一句自己的文案） |
| 前端 `HealthMetrics` / `RatioCard` | 挂载气泡；应急金额外在气泡里给出**本次 O / M / P / E 实际取值** |

🔴 **气泡里不许出现前端自己补的口径句子。** 后端常量改了公式，气泡必须跟着变；
前端补一句「其实是……」就等于口径有了两份，改后端时必然漏改。
`note` 由后端下发为**纯文本**（后端有用例守着「不得含 `**` / `==` 标记」）。

### 应急金的分母：12 个月三点估算

```
E = (O + 4M + P) ÷ 6      O=最小月  M=中位数  P=最大月
窗口 = 锚定月**之前**的 12 个完整月（不含盘点当月）
有支出记录的月份 < 3 → value = null（数据不足，不是 0）
```

唯一实现在后端 `services/expense_estimate.py`，**健康指标卡与比率面板共用**
—— 此前两处各算一套（卡片走未剔除转账的 SQL 全量），同名指标能差出好几个月。

界面上要同时给出两件事，缺一不可：

- **怎么算**（气泡里的公式与要点）
- **这次算出来是什么**（O / M / P / E 四行实际值 + 样本 `n / 12` 个月）

只有公式时无法判断这批样本厚不厚；只有数字时无法判断它稳不稳。

### 两条边界

- **不含盘点当月**：才过几天的月份会被当成完整样本，把基准拉低、月数抬高 ——
  那是往**乐观**方向错，最不该犯的方向。
- **只记收入没记支出的月份不算样本**：判据是「该月支出 > 0」而非「有账单行」。
  0 一旦进样本就顶掉 O。

## 生存资源盘点：盘的是物，不是钱（v3.59.0 一期 / v3.59.1 二期，P3-A）

`survivalStore` 是第六把尺子，也是唯一一把**量的不是钱**的尺子。
它和同 app 的金融资产体系**并列而不混同**：钱是 `WealthAsset*`，物是 `Survival*`。

| | `cashflowStore` 等（钱） | `survivalStore`（物） |
|---|---|---|
| 度量对象 | 金额存量与流量 | **物品存量与消耗速率** |
| 时间维度 | 月度快照序列 | 当前时点（快照留二期） |
| 结论形态 | 「能撑多少个月」 | 「能撑多少天 + 哪类先断」 |
| 是否能自我校验 | 有（借贷、转账成对） | **没有**（库存靠人录，系统无权质疑） |

最后一行是这一页最容易犯的错：**物这一侧没有天然的对账机制**。
系统不知道米缸里到底还有多少米，所以它唯一能做的就是**把口径摊开给人看** ——
这也是为什么口径气泡在这是必需项而不是加分项。

### 这一页的算法分派

组件**不判断该走哪条算法**。分派只看后端下发的 `consume_mode`，
**不看类别名** —— 把「吃」改名成「口粮」，页面照常工作。

| `consume_mode` | 走哪条路 | 明细面板呈现 |
|---|---|---|
| `meal` | 配餐：主食位求和 → 与必配位取最小 | 配方卡（早/正餐各自能撑多少顿） |
| `depreciation` | 按「一件还能穿多久」逐件折算 → 类内取最先穿坏的 | 物品表 + **衣物录入参考**（v3.59.8） |
| `on_demand` | 按「一份用多久」逐件折算 → 类内取最先耗尽的 | 物品表 |
| `time_based` | 按册数与节奏折算可读时长 | 物品表 |

⚠️ **「走哪条路」与「类内怎么聚合」是两件事**：前者看 `consume_mode`，
后者看类别的 `aggregate_mode`。上表第二列写的是各模式的**默认**口径
（`穿` / `用` / `医药` 现在都是「取最小」），用户可以在类别维护里改 ——
所以前端显示的是 `aggregate_mode_effective`，不是自己推导的值。

### 三条必须记住的口径

1. **`value === null` 不是 0。** 算不出来（类别下无可用物品 / 配方配置不全 /
   表未建立）一律 `available=false` + 值空 + `issues` 点名。
   「0 天」是一个**结论**（你一件都没有），与「还没录数据」不是一回事。
2. **配方 `trustworthy=false` 必须显式呈现。** 配料缺件时若静默跳过，
   这道菜会**算得更耐吃**（分母变小）。缺件要在卡上标出来、并说清缺哪件，
   而不是给一个看着正常的数字。
3. **三档区间不掩码、天数不掩码。** 天数与餐数是**非隐私的推导值**
   （与 `goals.progress_percentage`、比率面板同一条判据）；
   物品的**数量与金额**才是金额类，走 `formatAmount`。
   别顺手给「还能撑 47 天」加星号 —— 掩了之后这个页面就没有意义了。

### 前端只做三件事

| 做 | 不做 |
|---|---|
| 按 `consume_mode` 选组件 | 不判断该走哪条算法 |
| 按后端 `bands` / `SURVIVAL_METRIC_NOTES` 渲染口径气泡 | **不写一句口径文案、不定义任何判定线**（`bands` 恒为空数组） |
| 格式化天数 / 餐数 / 三档区间（`utils/survivalFormat.ts`） | 不做任何除法或聚合 |
| 按「最久没盘」排序与批量挑件（`utils/survivalStocktake.ts`，v3.60.2） | **不自己判「该不该盘」** —— `stocktake_due` 恒由后端下发（「没设周期就不催」那条规则在后端） |
| 记录面板的拍平与分组（`utils/survivalStocktake.ts`，v3.60.3） | **不在这里写列清单** —— `flattenStocktakeRows()` 造行、`recordSpan()` 给合并跨度；「哪些列是记录级」是 `STOCKTAKE_RECORD_PROPS` 一个集合 |

🔴 **`survivalFormat.ts` 里不许出现档位常量。** 「多少天算够」是使用者自己的标准，
系统一发明阈值，「生存天数」就从事实变成了评分。

### 两个易错点

- **`aggregate_mode_effective` 而非 `aggregate_mode`**：配餐类的聚合口径固定取最小，
  后端会把**实际生效值**下发，界面显示它。显示用户填的值会出现「写着求和、算取最小」。
- 🔴 **必配位是三态，不是两态**（`required_line_count` 必须与 `required_servings` 一起判）：
  `required_servings === null` 有两种来由 ——
  `required_line_count === 0` → **「无必配项」**（正常配置，无约束、不参与结论）；
  `required_line_count > 0` → **「算不出来」**（真有问题，`issues` 会点名哪件食材）。
  ⚠️ 一律渲染成「算不出来」会造出自相矛盾：旁边「配方可支撑」算得好好的，
  这一格却说算不出来，使用者会以为配错了 —— 而其实什么都没错。
- 🔴 **衣物录入参考是「提示」，不是「兜底」**（v3.59.8）。它讲的是
  「别人一般填多少」（`meta.wear_reference`，由后端常量下发），
  **算法一个字段都不读它**。三条不许破：
  ① 不预填 —— 名称里带「T恤」也不自动写值，否则会造出「我没动过它却变了」的账；
  ② 不兜底 —— 口径没填就是「算不出来」，让参考值顶上会给出一个**看着合理**的天数，
     比报错难查得多；
  ③ **`uses_*`（可穿次数）与 `days_*`（可用天数）不互相换算** —— 次数与穿法无关、
     跨人可比，天数隐含了一个穿着频次。拿天数反推次数，得到的是一个没人核对过的假设。
  另：「一件还能穿多久」不是常量（遮体保暖 vs 体面差 3 倍以上），
  所以这页**绝不给衣物定一条判定线** —— 参考值只是锚点，手感优先。
- **弹窗里的输入与联动预览不掩码**（输入态），但**列表行与明细表掩码**
  （已落库数据的呈现）—— 见 §隐私 v3.58.18 覆盖范围判据。
  同一文件里两类常并存，逐处判定，别批量替换。

### 二期：单位就地新增 + 盘点历史（v3.59.1）

**① 单位就地新增。** 单位是「录物品时才发现缺」的东西，
把它推到页面顶部先加好，等于要求使用者先知道后面会缺什么。
所以物品与配方对话框的单位下拉底部各挂一个「+ 新建单位」。

⚠️ 实现是**浮层对话框**（`SurvivalUnitQuickAdd.vue`，`append-to-body`），
**不是**「在下拉里嵌一个内联输入框」：`el-select` 的下拉在失焦与选项交互时会关闭，
输入框放进下拉内部，键一敲、焦点一动就丢。浮层挂 `body` 才与下拉生命周期解耦。
下拉底部的按钮要加 `@click.stop`，否则下拉会先收起、弹窗起不来。

**② 盘点历史**（`SurvivalSnapshotPanel.vue`）：一期只回答「现在能撑多久」，
那一个数字**每看一次都像第一次看**；二期给出方向。

三条展示判据（写在组件头注释里，别删）：

| 判据 | 为什么 |
|---|---|
| **空值不补 0，折线断开** | 补 0 会画出一条「那天物资归零」的**假线**，比没有线更糟。某期算不出来时，差值是「不知道」不是「没变化」 |
| **不可比就显示 `reason`** | 两次之间改过类别或消耗模式的话，天数的差里混着「换了算法」这一项。照常显示差值 = 把配置变更说成了物资变化 |
| **天数不掩码** | 天数是推导值、不是隐私项（同 `progress_percentage` 与比率面板）；**备注**是自由文本，才走 `maskFreeText`。别顺手给「还能撑 47 天」加星号 |

⚠️ **折线颜色刻意不套「涨红跌绿」**：那套是**价格**语义。
天数变长是好事，所以颜色**跟语义走、不跟数值方向走**（`survivalFormat.deltaType`）。
这一页是「涨红跌绿」的**唯一例外之外**的例外 —— 见项目记忆里的配色例外条款。

⚠️ **前端不做减法**：`delta_expected` / `delta_kind` / `days_since_previous` 全部由后端算好下发，
前端只上色与格式化。`takeSnapshot` 遇到 400（同一天重复盘点）**原样抛出**，
由面板问「要不要覆盖」，不吞成 `false`。

### 三期：按次计量 + 物品清单 + 实盘盘点（v3.59.3）

页面下方现在有**三块并列**，分工不能混：

| 面板 | 数据来源 | 回答 |
|---|---|---|
| **物品清单**（`SurvivalItemLedger.vue`） | 主数据 + 工作表 | 我有哪些东西；哪些该盘、哪些该补货 |
| **实盘盘点记录**（`SurvivalStocktakePanel.vue`） | **人数出来** | 实物与账面差多少 |
| **生存时长快照**（`SurvivalSnapshotPanel.vue`） | **系统算出来** | 比上次是变长了还是变短了 |

⚠️ 第三块原名就叫「盘点历史」，v3.59.3 **正名为「生存时长快照」**：
它是系统算的结论，不是人数出来的实物数。两个都叫「盘点」，
「我到底盘没盘过」就永远说不清。**只改名字与文案，行为未变。**

**① 按次计量。** 物品不是天天用的东西（卫生巾、电池、滤芯）按「一份能用多少天」填不出来 ——
它取决于「多久用一次」。所以计量方式二选一：按天 / **按次**（一份能用 N 次 × 每 M 周期用 K 次）。

| 判据 | 说明 |
|---|---|
| **前端不做折算** | 弹窗里只把四个字段**拼回一句人话**（`每 3 天用 1 次`）。要做实时预览就得把「周期 → 天」的系数下发到前端，那正是第二份口径 |
| **切口径时显式送 `null`** | 后端判据是「填了「一份能用几次」就按次算」。不送 `null` 会留下一条界面上看不见、算法里还算数的旧口径 |
| **显示 `days_per_unit_effective`** | 按次物品的 `days_per_unit` 是空的，直接读会把「换了个填法」显示成「没填」 |

**② 物品清单**是跨类别的全量台账（一期二期只有按类别摊开的视图，盘点需要一份不分类的总账）。
点「编辑」时**必须把物品自己的类别带到弹窗**：那件物品的类别往往不是当前 tab 停的那一类，
沿用当前 tab 会按错的 `consume_mode` 显隐字段 —— 配餐类根本不显示「一份可用天数」，
用户会以为那个值丢了。所以 `SurvivalView` 单独存一份 `itemDialogCategoryId`。

随时间变的列（上次盘点 / 该不该盘 / 是否低于补货线）**一律取自工作表**，不从 `items` 里自己判：
「没设周期就不催」这条规则在后端，在这里重写一遍迟早会漏，然后所有物品一起标红。

**③ 实盘盘点弹窗**（`SurvivalStocktakeDialog.vue`）三条判据（v3.60.2 又在它之上加了
「只列挑中的那几件」与单件入口，见下方**五期**）：

| 判据 | 为什么 |
|---|---|
| **未勾 = 不盘** | 只提交勾上的那些。把未勾的当 0 提交等于**一键清空库存** —— 这是这一屏最容易出灾难的地方 |
| **账面只回显、不提交** | 真写入时服务端会再读一次（防的是盘点页开着半小时、其间库存在别处变过）。盈亏的实时差**只是回显，不是口径**，最终以后端返回为准 |
| **提交前说清「会校准库存」** | 它是改账的动作，不是只读核对。这句话写在按钮上方，确认框里再说一次 |

🔴 **盘盈盘亏不套「涨红跌绿」**：那套是价格语义。差异只说明实物与账面不一致 ——
亏了要去看是不是消耗比记的快，盈了要去看是不是漏记了消耗，两边都不是单纯的好消息或坏消息。
所以只按「要不要留意」上色：核对无误给绿（唯一确定的好结果），有差异给提醒色（`deltaKindType`）。

⚠️ **盈亏符号必须显式给**：`+2` / `-6` / `0`。只给绝对值时「多了 6 件」与「少了 6 件」
长得一模一样，而它们要采取的行动完全相反。

⚠️ **删除盘点记录不会回滚库存**（后端铁律三）。确认框里必须写出这句 ——
不写，用户会以为「删掉 = 撤销那次盘点」，而库存一点没变。要改数量去编辑物品。

⚠️ **明细随列表一起返回**（与快照列表「刻意不带明细」相反）：盘点的明细就是内容本身 ——
只给「盘了 12 项、3 盈 2 亏」，还得再点一次才知道是哪三件，等于把唯一的答案藏起来。

**④ 实盘盘点记录**（`SurvivalStocktakePanel.vue`）—— **阅读型面板**，
v3.60.3 从「主表 + 展开子表」改成「一套网格 + 行合并」：

优化前是 5 列主表 + `type="expand"` 6 列子表 = **11 处列定义、两套宽度**，
展开后左右两端都不齐；而**想知道盘了什么必须先点开**，实测 8 条记录里 **6 条只盘了一件**。

| 判据 | 为什么 |
|---|---|
| **明细直接成为表行，记录级字段跨行合并** | 读全历史从「18 行 + 点 8 次」变成「10 行 + 0 次」。记录级 = 盘点日 / 结果 / 备注 / 操作，判定走 `STOCKTAKE_RECORD_PROPS`（按 **prop** 判，**不按列序号** —— 序号一改合并就会错到别的列上，而画面看着仍然正常） |
| **账面与实盘合成一列** | `5 件 → 4 件`。账面 / 实盘 / 盈亏三个格子说一件事，读者不必自己做两遍减法 |
| **日期格补「录入时刻」，措辞写「录入」** | 实测 **6/8 条记录落在重复日期上**，只靠备注区分不了。`stocktake_date` 是业务日期（可补录）、`created_at` 是系统时刻，两者不同义；时刻用**字符串切片**取（`formatClock`），**不解析 Date**（服务端已本地化到 `+08:00`，再解析一次就是两把尺子） |
| **空备注留白，不用「—」** | 备注的「空」只有一种含义（数值的 `null` 才有歧义）。实测明细备注 0/10 有内容、记录备注 5/8 是空 —— 一屏 15 个破折号全是噪音 |
| **行备注整表有内容才成列** | 按「整表」判而非「按组」判 —— 按组判会让同一张表里各组的列数不一致 |
| **件数只在 ≥2 件时写** | 单件写「1 件」是噪音（实测 6/8 条是单件） |
| **删除收进「⋯」下拉** | 8 个常显红字 → 8 个灰点；红色是界面最强权重，不该给最不该顺手点的动作。菜单项写明「库存不回滚」 |
| **汇总行只给次数与行数** | 🔴 **不给「总盈亏」**：单位不同不能相加（盒/片/千克/罐/抽），`+6 盒` 加 `+50 抽` 没有意义 |

⚠️ 没有明细的盘点**仍占一行**并明说「这次盘点没有明细」——
静默吞掉一行记录，比显示一行「没有明细」糟得多。

❗ **`span-method` 是本项目首次使用**：合并行为（与 `row-key`、动态列叠加时）
尚未在应用内验证，只做了类型检查 + 拍平逻辑的一次性脚本验证。

### 四期：三块拆成页签（v3.59.4）

三块面板原先是**竖着堆**在同一屏上的，越堆越长。现在改为**页内吸顶页签**：

| 页签 | 内容 | 角标 |
|---|---|---|
| 总览 | 四类卡 + 类别明细 + 配置问题折叠 | — |
| 物品清单 | `SurvivalItemLedger`（**盘点唯一的挑物品入口**，v3.60.2 起） | **该盘 N** |
| 实盘盘点记录 | `SurvivalStocktakePanel` | — |
| 生存时长快照 | `SurvivalSnapshotPanel` | — |
| 库存流水 | `SurvivalFlowPanel`（**v3.60.18 新增**，第 5 个；见下「十四期」） | — |

四条判据：

| 判据 | 为什么 |
|---|---|
| **结论条留在页签外** | 「综合能撑 / 钱能撑 / 瓶颈」是本页唯一的产品答案。塞进某个页签 = 停在「物品清单」就看不见还能撑多久 |
| **`v-show` 而非 `v-if`** | 清单的勾选与筛选是**跨页签的中间态**（勾好要盘的几件 → 去快照页看一眼 → 回来接着开盘点）。`v-if` 卸载会静默清空，用户会以为勾选没生效 |
| **角标只挂「该盘 N」** | 判据：看了会改变行为的才加。总件数、快照期数看了也不会改变任何行为 |
| **页头按钮下沉** | 「新增物品」「开始盘点」在各自面板头已各有一份，页头不再重复 |

⚠️ **抄的是 `WealthHub` 的观感，不是它的路由结构**：WealthHub 的六个 tab 是六个不同实体、
各自取数；生存页只有**一个实体**（一批物资），四块是它的四个视角 —— 页内页签切一次 **0 请求**
（`onMounted` 一次 `fetchAll()`），路由级页签每切一次都要重新 mount 取数、
还会被 `resetState()` 清掉中间态。判据一句话：**tab 的数是不是同一个实体**。

### 五期：盘点交互优化（v3.60.2）

起因是用户一句「物品多了之后盘点不好操作」。先看数据（开发库只读实测）：
7 天内 6 次盘点、共 **8 行**明细、平均每次 **1.3 行**，其中 4 次只盘了 1 件
⇒ **真实用法是「随手抽查一两件」**，而交互是为「坐下来盘全库」设计的。

三条根因：

| # | 根因 | 处置 |
|---|---|---|
| ① | 「勾上该盘的 N 件」依赖盘点周期，而**一件都没设过** ⇒ 恒灰，且不解释原因 | 保留原判据（「从未盘过」不算该盘，否则全标红 = 没有标），**另加零配置入口**「勾上最久没盘的前 10 件」，并在原位置说出为什么没有「该盘的」 |
| ② | 挑物品做了两遍（清单 5 个筛选 vs 弹窗 1 个），批量勾选两份实现 | 挑物品**只留物品清单一处**；判据抽到 `utils/survivalStocktake.ts` **单一实现** |
| ③ | 后端 `get_worksheet` 早已支持 `item_ids`，前端永远空调用 ⇒ 为盘 1 件拉全量 | 单件盘点走 `fetchWorksheetRows([id])` |

三条判据：

| 判据 | 为什么 |
|---|---|
| **弹窗只列挑中的那几件** | 路径从「勾选 → 打开全量表 → 再找一遍 → 填数」变成「勾选 → 填数」。中间那段是纯损耗 |
| **`fetchWorksheetRows` 不写共享状态** | 全量那份同时喂着清单页与类别明细的「上次盘点」列。只取子集会把那两处**打空，而界面不会报错** |
| **排序 ≠ 标签** | 「从未盘点」排在「最久」位置（它确实离得最远），但**仍不打「该盘了」标签** —— 原判据完整保留 |

⚠️ **「上次盘点」由 `formatLastStocktake()` 产出整格字符串**（`2026-09-23 · 6 天前`）。
在此之前它是两个相邻 `<span>` 靠 CSS `margin-left` 拉开 ——
**漏写那个 class 的地方就粘成了 `2026-09-236 天前`**（清单页正常、盘点弹窗里粘住）。
分隔符比间距稳，且三处调用从此共用一份。

⚠️ **单件盘点的 `lines` 永远只有一行**：用户只数了这一件，多写一行等于替他宣称
「另一件我也数过了」。

⚠️ **「改库存」与「改主数据」是两个入口**：想改数量走「盘一下」（会留盘点记录），
改名称 / 单位 / 类别 / 计量口径走「编辑」。在此之前前者只能借道后者。

⚠️ **未做浏览器冒烟**：本沙箱 `vite build` 会被 safe-delete 守护拦截（环境拦截、非代码错），
本次只做了 `vue-tsc --build` + 探针验证。

⚠️ 结论条不自己留下间距，首块内容的 16px 留白由各块自己给（卡片区 `margin-top`、
三个面板自带 `margin-top`），否则会多出一条松散缝。

⚠️ 上面「下划线通栏」那几句在 v3.59.5 已不适用 —— 页签挪进了页头，
下划线样式随之换成行内胶囊，见下一节。

### 五期：类别可选 + 页签并入页头（v3.59.5）

**① 新增物品可选类别。** 原先 `SurvivalItemDialog` 的 `categoryId` 是必填 prop，
`openItemDialog()` 一律传 `store.activeCategoryId` —— 从「物品清单」点新增，
永远落进总览当前停的那一类（默认「吃」）。改法是把类别升为**表单字段**：

| 位置 | 不同步会出现什么 |
|---|---|
| 整组按类别分派的计算属性 | 读 prop ⇒ 改了类别、字段没跟着变 |
| `unitOptions` | 单位是类别私有的（「罐」不属于「穿」），旧单位在新类别里不存在 |
| `submit()` 里的 `category_id` | 传 prop ⇒ 用户刚选的类别被丢掉，静默存回默认那一类 |

⚠️ `form` 的声明必须提到计算属性**之前** —— 这组计算属性现在依赖 `form`，
`const` 的 TDZ 会让「先算后用」变成启动即崩。

⚠️ 换类别时 `onCategoryChange()` **清掉上一类的模式专属字段**：把「一件可用天数」
原样带进配餐类，等于给新类别塞一个没人核对过、界面上还看不见的数。

⚠️ **编辑时类别只读**，以物品自己的类别为准：后端 `category_id` 确实可写，
但「配方行的物品必须属于该配方类别」这道校验只写在**配方**一侧 ——
被配方引用的物品一旦改类别，配方里会留下一个别类的食材，而且没有任何地方报错。

**② 页签并入页头。** 「四卡提到综合能撑下方」与「页签放到标题右侧」其实是同一个解：
页签原来自己占一行、正好夹在结论条与四卡之间，挪进页头后四卡自然就贴了上去。

| 判据 | 说明 |
|---|---|
| **行内胶囊，不用下划线** | 下划线要有通栏底线才像导航，而这一行左边是标题、右边是配置项，底线会横穿整条头部。激活色仍是分组主题色 `#f39c12` |
| **副标题收进标题旁的 ⓘ** | 一行要装下 标题 + 4 页签 + 3 配置项 ≈ 1016px，正好卡在折行边缘。副标题（约 376px）是一次性阅读的图例，不该长期占位 |
| **头部整体吸顶** | 页签就在这一行里，滚下去不该把导航一起滚走；底色取 `--lm-bg-secondary`，用负边距通栏 |
| **窄屏折行可接受** | 页签内边距 16 → 12px、日期框 180 → 160px 已腾出约 80px 余量；再窄交由 `flex-wrap` 处理 |

### 六期：按天口径的频次字段改为可空（v3.59.6）

**症状**：按天计量填完点保存 → 界面只回一句「保存失败」，而表单里没有一处像填错。

**根因**：是**「可空」这件事有两份说法**：

| 层 | 按天口径下的表现 |
|---|---|
| 前端 payload | `uses_per_unit` / `use_cycle_num` / `use_times` 送 `null`，`use_cycle_unit` 送 `'day'` |
| 后端序列化器 | 前两个 `allow_null: True`，第三个没声明（⇒ 不许为 null） |
| 数据库列 | 三列全 `NOT NULL` ⇒ `IntegrityError (1048)` ⇒ **500** |

`'day'` 那个值是当年为了迁就 `NOT NULL` 的列顺手写的 —— **一列迁就、两列不迁就**，
不一致本身就是病灶。

**改法**：`submit()` 里三个频次字段**一起送 `null`**；
`SurvivalItemFormData.use_cycle_unit` 放宽为 `string | null`。

⚠️ **置空的判据不在这边** —— 后端 `validate()` 里写着
「没有 `uses_per_unit` ⇒ 三个频次字段一律置空」，客户端送什么都一样；
这边的显式 `null` 只是把话说清楚，不是不变量本身。

⚠️ **读侧仍然是 `''`**（后端 `_item_row` 里 `or ''`）：与 `satiety` / `grade` / `priority`
这些可选 CharField 同一惯例，**别按「可空」去改读侧类型**。

⚠️ 保存失败时的提示：`extractMessage` 现在会在**拿不到字段级原因、且状态码 ≥ 500** 时
补一句「服务端错误 NNN，请查看后端日志」—— 一次服务端异常与一次「我填错了」
不该长得一模一样（这次排查有一半时间耗在这句话上）。

### 七期：必需品基准清单与缺口对账（v3.59.7）

**这一期补的是「我漏了什么」** —— 天数回答「够撑多久」，但它答不了这件事：
没录入的东西不在公式里，就不构成缺口（实测「用」类底下只录了 2 件，
牙膏、洗发水从来没进过系统，而短板照样理直气壮地判在「吃」上）。

**新增两个组件**：

| 组件 | 作用 |
|---|---|
| `SurvivalEssentialPanel.vue` | 缺口对账卡 + 基准清单（可增删改、**可关联一组已有物品**（v3.59.12）、可一键初始化） |
| `SurvivalEssentialDialog.vue` | 基准项的新增 / 编辑弹窗（对应物品**多选**（v3.59.12）） |

挂载位置：`SurvivalView.vue` **总览 tab 里四张类别卡之下、类别明细页签之上**。
判据：它是**结论层**信息（「你漏了什么」），不是某一个类别的下钻 ——
放进某一类里会变成「这一类漏了什么」，而真正的缺口往往落在**你还没建的那个类别**里。

⚠️ **上面那句挂载位置在 v3.59.9 已不适用** —— 对账搬到了**页头右侧的一个入口**
（见下面「八期」）。「是结论层、不是某一类的下钻」这条判据仍然成立，
变的是它**不该占着「还能撑多久」那一屏**。

**前端只做两件事**：

1. **按后端给的 `level` 上色**（五档：未录入 / 待补数据 / 告急 / 偏紧 / 充足）；
2. **按后端给的顺序渲染**（默认按紧迫度：核心优先 → 档位严重度 → 天数升序；
   管理界面要看录入顺序时传 `sort=order`）。

⚠️ **不重算分档、不折算天数** —— 阈值真源在后端 `SURVIVAL_ESSENTIAL_LEVEL_FLOORS`，
前端再写一遍判档迟早不一致，而不一致是**静默**的（两边都会显示出一个看着合理的颜色）。

⚠️ **未录入与待补数据必须分开显示**：一个要去录入（或确认自己根本用不着、那就删掉这项），
一个是物品在、用量口径没填。两者都要人动手，但动的是**不同的手**；
一律渲染成「算不出来」会把「还没录数据」说成「配置出错」，令人去改一个本来没坏的东西。

⚠️ **`missing_categories` 必须说出来**：初始化基准清单时若某个类别还不存在，
后端会**跳过**那些基准项并报告类别名（凭空建类别会绕过「不预设用户分类结构」那条判据）。
前端把跳过的类别显示出来 —— 静默跳过会让人以为清单本来就这么长。

⚠️ **「初始化默认类别」改了两处行为**（本轮自造的缺口，写文档回查代码时才发现）：

1. 成功文案补上「医药」（原先写死「吃 / 穿 / 用 / 数字」四类）；
2. 类别已存在时**先问一次**是否把类别口径覆盖为当前默认值 ——
   `seedDefaults()` 的 `overwrite` 默认 `false`，而**默认口径会随版本变**
   （v3.59.7 把「用」、v3.59.8 把「穿」由求和改成取最小），只在首次创建时生效的话，
   **老库会一直跑着旧口径，而界面上看不出任何差别**。确认文案要写清
   「会冲掉你在界面上改过的类别口径、以及基准项的性质与提示；
   **已关联的物品不受影响**」（后端 `seed_essentials(overwrite=True)` 只改
   category / scope / unit_name / hint / sort_order，**不动 `items`**）。
   入口位置在 v3.59.10 变过一次（从页头主按钮收进「配置」下拉，见「九期」）——
   **行为没变**，上面这两条仍然成立。

### 八期：缺口对账从正文搬成页头入口（v3.59.9）

**起因**：对账先前嵌在总览（四卡之下、类别明细之上），于是每次看「还能撑多久」
都要先路过一张二十来行的表 —— 而「够撑多久」与「漏了什么」本来就不在同一个问题上。

**改法**：`SurvivalView.vue` 页头右侧加一个入口按钮，点开 `SurvivalReconcileDialog`
（`el-dialog` + `embedded` 面板）。总览正文不再有它。

🔴 **搬的时候必须把「可信度信号」一起搬出来** —— 这是本次唯一容易做错的地方：

`unclosed_core`（核心项还没闭合）原先靠正文那块卡可见，搬进弹窗后**页头上就没有第二个落点**。
而它**不折算进天数**（未录入的牙膏不进公式 —— 把「还没录」说成「只够撑 0 天」
是另一个错误），所以它是「这份结论能不能用」的**唯一提示**。
⇒ 入口按钮**必须带角标**，见 `SurvivalView.essentialEntry`：三态各自指向不同动作，
不合并成「有 / 无」：

| 角标 | 含义 | 该做什么 |
|---|---|---|
| （无） | 核心项已全部闭合 | 进去只是看一眼 |
| `待初始化`（中性色） | 还没建基准清单 | 去点「初始化基准清单」 |
| `还差 N 项`（警示色） | 有核心项没闭合 | 去把它关联 / 录入 |

⚠️ 角标的数字取 `analysis.essentials.summary.unclosed_core_count`（后端算好的那一份），
**不在前端对 `essentials` 数组自己数一遍** —— 数一遍就会出现「入口说还差 3 项、
弹窗里明明 4 项」这种自相矛盾，而原因仅仅是其中一处忘了刷新。

⚠️ 入口按钮与四个页签**同一条件显示**（`analysis?.available`）：迁移没跑 / 表还没建时
对账也无从谈起，留一个点开只有空壳的入口比不放更费解。

⚠️ `SurvivalEssentialPanel` 的 `embedded` 是**纯外观开关**（去外壳 + 去自带标题，
避免弹窗里「框里的框」和两行一样的标题）：它不参与任何取数、展示或分档。
若哪天它开始影响内容，说明有人在壳里做了业务判断，那应该收回面板里。

⚠️ 弹窗挂 `destroy-on-close` 不是随手加的：明细由面板 `onMounted` 取
（`store.fetchEssentials()`），销毁重建 ⇒ **每次打开都重新拉一次**，
关闭期间在别处改过的关联不会以旧快照的形式显示。去掉它就会变成
「只有第一次打开时取数」，而界面上完全看不出它没刷新。

### 九期：结论条补口径 + 类别入口归并（v3.59.10）

起因是站在产品视角做的一轮排版 / 交互审视，结论条与类别切换各有一处结构性问题。

**① 结论条上四个数，一个口径气泡都没有。**
四张卡各自挂 ⓘ，而**最靠近答案的一行反而是全页唯一没有口径可达性的地方** ——
`SURVIVAL_METRIC_NOTES` 里的 `pert_expected` / `bottleneck` / `coverage` 早就下发了，
只是没人接。现在四个数各挂一颗，统一走 `bannerMeta(key)`。

⚠️ 「钱能撑多久」此前**没有可挂的键**（只在 `bottleneck` 的 note 里被顺带提过一句），
所以同步在后端补了 `SURVIVAL_METRIC_NOTES['cash_days']`。
**前端不许在这里补一句自己的解释** —— 那就成了第二份口径。

⚠️ 键名写错时 `MetricTooltip` 是**静默不渲染**（`v-if="meta"`，而不是渲染一个空气泡），
界面上完全看不出「本来就没打算加」。所以 `test_survival_banner_meta.py` 里那份
`BANNER_KEYS` 名单必须与前端调用逐字对应。

**② 类别有两套控件做同一件事。**
四卡可点（`@select`）、下面那排 `el-tabs` 也可点（`onTabChange`），绑的是**同一个**
`activeCategoryId`，视觉语言还不同。现在撤掉页签行，四卡是唯一的选择器。

⚠️ 撤掉它有个连带代价：那排页签**兼职做着明细区的标题**。
所以明细区补了一行 `{类别} · 明细`（`activeCategoryName`）——
不补回来，那块内容就没有标题了。

**③ 参考日期原先是个空框。**
`''` = 今天，但空框与「用户清空了日期」在视觉上是同一个东西，
用户**无从知道现在算的是哪一天**。同 `formatStocktakeGap` 那条规矩：
空值不许重载两种含义 —— `''` 就是今天，那今天就得说出来。
现在 `referenceDateValue = store.referenceDate || todayISO`，
且 `localToday()` 用**本地日期拼**，不用 `toISOString()`（后者是 UTC，
UTC+8 的凌晨会得到「昨天」，与后端 `date.today()` 对不上）。

**④ 「初始化默认类别」是破坏性的，却与查看类操作同权重。**
它会弹「覆盖类别口径」、冲掉界面上改过的消耗模式与说明文案，
原先却和「单位维护」并排占主按钮位，看着像一次无害的补齐。
现在两者一起收进「配置」下拉，危险的那一项**带副标题把后果写出来**。

⚠️ 顺带：卡片上离差与区间的单位统一了（`formatSpread` 复用 `formatDayQuantity`）。
此前「穿」卡是 `18.5 年 ~ 30.0 年 · ± 701.9 天` —— **同一行两把尺子**。

### 十一期：「一份」绑定数量单位 + 保存前试算（v3.59.11）

起因是一条真实数据报错：洗脸巾「数量 300 抽 + 一份能用几次 300 + 每 1 天用 2 次」，
页面报 **123.7 年**。**算法没错** ——

```
天数 = 数量 × 一份能用几次 × (周期天数 ÷ 每周期次数) = 300 × 300 × 0.5 = 45,000 天
```

错在**同一个 300 被填了两遍**：一次是「我有 300 抽」，一次是「一份里有 300 抽」。

**① 「一份」这个词原先没有落点，而且唯一的提示语教错了方向。**
这一格的提示原文是「一包 10 片就填 10；一瓶 30 粒就填 30」——
它把「一份」定义成**包装**；而用户的「数量」是拿**内容物**（抽 / 片）填的。
两个口径一混，300 就出现两次。现在标签跟着**数量的那个单位**走：

| 数量 | 这一格填 | 读作 |
|---|---|---|
| `300 抽` | `1` | 每抽能用 1 次 → 300 × 1 × 0.5 = **150 天** |
| `1 包`（一包 300 抽） | `300` | 每包能用 300 次 → 同样 150 天 |

两种填法都对，**但两个数不能同时指向同一批东西**。`usesLabel` 由
`unitName` 派生（`每抽能用几次`），`cycleReadOut` 同步改成同一个单位 ——
否则「一份」又成了一个没人定义过的词。

**② 这个表单从来没把数乘出来给人看过。**
中间量「一份可用 150 天」完全正常，错在最后一跳（乘以 300）。
所以挂一条**保存前试算**：填完就显示最终会存进去的那个数。

🔴 试算走**后端**（`POST /survival/items/preview/`），不在前端自己乘。
前端乘一遍确实更快，但那会得到**第二份公式**，而两份公式迟早分叉 ——
分叉是静默的：试算说 150 天、保存后写着 123.7 年，两边都像个正常的数。
后端那个端点用**同一行代码**（`compute_item_life`）+ **同一个表单序列化器**，
所以「试算放行、一保存报 400」也不可能发生。

⚠️ 试算是**护栏不是闸门**：它自己失败（网络 / 后端挂了）只降级成一句
「试算暂时不可用（不影响保存）」，绝不阻断保存。

⚠️ 它刻意**不走 store**：store 的动作都在管 state（`saving` / `refreshAll`），
试算是只读探询、不产生状态。挂进去会连 `saving` 一起点亮，
于是「正在保存」的转圈会在用户每敲一位数字时出现 —— 那是假的。

⚠️ 提交负载抽成了 `buildPayload(categoryId)`，**试算与保存共用一份**：
复制成两份就是「试算按 A 校验、保存送 B」，两边各自都自洽，
合起来是一个只在某个字段上出现的幽灵。

⚠️ 明确**没做**：按「天数太大」告警。衣物按天口径下「10 件大衣 = 30 年」
完全正当，用阈值判会频繁误报；真正精准的那个判据（数量与一份次数相等）
属于启发式，本轮不做 —— 试算把两个数并排念出来已经够了。

**明确没做**：卡片空状态（「算不出来 / 还没有可用物品」）加行动指引；
卡片用上后端已下发、目前被丢掉的类别 `description`。

### 十二期：一条基准项可以挂多件物品（v3.59.12）

原来「对应物品」是**单个**外键，逼用户在「夏季睡衣」和「冬季睡衣」里二选一 ——
而无论选哪件都答不对「睡衣还能撑多久」：冬天还是没得穿。
现实里一条基准项常常需要几件**并列**才成立：

    睡衣分夏 / 秋 / 冬    卫生巾分日用 / 夜用    鞋分室内 / 室外

**判据与类别口径同源**：可替代才求和，并列缺一不可就取最小。
组内**取最小、不求和** —— 而这个方向是**刻意选的保守**：
算错成「虚报缺口」，用户在界面上看得见、会去核实；反过来求和错了是「掩盖缺口」，
静默且危险（「用」类曾被一件洗脸巾撑到 4.5 万天，牙膏剩 5 天没人看见）。

⚠️ **三档是逐档取最小**，不是「挑出最短那件、再抄它的三档」——
一件有到期日封顶、另一件没有时两条曲线会**交叉**（A 的乐观档最短、B 的悲观档最短），
抄一件必然漏掉另一件的短板。这一点有专门用例：
`test_survival_essential_multi.py::test_each_scenario_takes_its_own_minimum`。

⚠️ **只要一件算不出，整条报 unknown**，`expected` 也回到 None ——
不拿部分数据充完整答案（把「有一件还没填口径」说成「另外两件能撑 300 天」，
用户看到 300 天就不会去补那一件了）。`items[]` 里算不出的排在**最后**：
有数字的是**结论**，算不出的是**待办**，不该混在一起排。

**前端三处**：

| 位置 | 变更 |
|---|---|
| 「对应物品」行内下拉 | 改 `multiple` + `collapse-tags` + `collapse-tags-tooltip`（三个季节的睡衣不把行高撑起来；折叠后仍看得见全选了哪几件，少了它用户会以为只挂上了一件） |
| 「可支撑」悬浮 | 单值时的 `content` 字符串换成 `#content` 插槽：逐件列出 + 代表件加粗 + 「共 N 件并列，取最短那件」 |
| 基准项弹窗 | 同款多选；回填取 `row.items` 而不是顶层的 `item_id` |

⚠️ 悬浮用**行内样式**而不是 class：tooltip 的内容会被 teleport 到 body，
scoped 样式够不着它 —— 用 class 会一行样式都不生效，而且不报错。

⚠️ 顶层 `item_id` / `item_name` 现在的含义是**代表件**（正常用量下最短的那件），
不再是「唯一那件」。回显时填 `row.item_id` 会把另外几件静默丢掉 ——
用户一保存就少了两个季节的睡衣。

⚠️ **空数组 ≠ 不传**：空数组是「用户把勾选全取消了」，不传是「这次不动它」。
后端认这个区别；前端写成省略就会让清空退化成不动 ——
界面看着清空了、刷新又回来。同理，多选下拉的 change 要先比**集合**
（`sameIds`）再决定要不要发请求：取消一个又勾回同一个也会触发 change。

⚠️ **明确没做**：「这条基准项该有几件」。挂了夏季睡衣、秋 / 冬还没录时，
系统算出的天数只看夏季那件，**看不出你挂少了**。
多选让用户能挂 3 件，但用户挂 1 件时系统分不出来 ——
它得先由用户告诉它「该有 3 件」，那是另一个字段、另一件事。

### 十三期：组合配置 —— 分开登记、一起下锅（v3.59.13）

「燕麦米 / 绿豆 / 薏仁 / 紫米**分开登记**（各自算数量、各自算保质期），
但烹饪时**一起下锅**。」登记与「一起用」是两件事 —— 组合只管后者。

**组合在配方里占一行**，不展开成四行。展开在挂主食位时与一行**数学等价**
（`min-of-min = min`，后端有用例钉住），但它买到三个坏处：
列表膨胀四倍、「这四件是一锅的」这个事实消失、
**改组合时已展开的四行不会跟着改 ⇒ 静默分叉**。
所以「不展开」是**展示层的选择**，不是算法上的妥协。

⚠️ **组合行没有「每餐用量」这一格**，也**没有份数 / 倍率**。
用量写在组内每一件上（建组合时填），这里再乘一次就是「两个数相乘」的形状 ——
两个数各自看着都正常、乘起来才错、而界面上看不出来（v3.59.11 那个 45,000 天
就是这个形状）。这一格显示「**用量见组内各件**」：
**不能留空**（空白会被读成「还没填」，而这个格子的正确状态就是「没有」），
**也不能显示 0**（0 会让人以为这一行不消耗）。
为了让行与行对得齐，这个格子用一段说明把宽度**占住** ——
直接留空会让下面的行整体左移，看起来像表单坏了。

⚠️ **一行用一个 `rows` 数组承载，不用 `lines` + `comboLines` 两个**：
两个数组会渲染成两块，而配方本来是一串顺序的行；用户想「第三行换成组合」时，
得先在一处删、再去另一处加。`source` 只活在编辑期 —— 后端是两张表，
提交时按它拆回 `lines` / `combo_lines`。

⚠️ **提交时两个键都送** = 以这张表单为准整体覆盖。只送 `lines` 的话，
后端会把「没传」理解成「这次不动它」，界面上删掉的那行组合会**悄悄复活**。

⚠️ **切换来源时两边的选择都要重置**（自动选中同侧第一项）：
留着一个隐藏的 `item_id` / `combo_id`，会让人以为「切回去还是原来那件」。

⚠️ **两个「加」按钮分开**（添加食材行 / 引用一个组合）：组合是个可复用的东西，
不该逼人「先加一行、再翻开关」才找得到。

**组合行的展示**（`SurvivalDetailPanel.vue`）：带「组合」标记并**摊开组员**
（`燕麦米 40 克 · 绿豆 30 克 · …`）—— 组员是这一行的**解释**：算出来的短板是
组内最先耗尽的那件，不列组员就没法理解那个数是怎么来的。
「每餐用量」显示「见组内各件」、「库存」显示「—」（明确表示「这里没有单一的数」，
而不是空白 —— 空白和加载中长得一样）。

**必需品候选的新过滤**（`SurvivalEssentialDialog.vue`）：
候选里**去掉已挂在别的基准项上的物品**（一件只能挂一处），
但**自己已勾的那几件必须留着** —— 否则连取消勾选都点不到。
被过滤掉几件会写进提示：**过滤必须可见**，
少了几件却没有任何解释，看起来像数据丢了。
⚠️ 跨类别或存量里确实挂了两处的物品也要保住：候选里没有它时 `el-select`
会把值当标签显示，界面上冒出一个裸 id（如 `42`），看起来像数据坏了。

⚠️ 弹窗只在 `store.essentials` 为**空**时取一次清单：
带参取一次会把清单页当前的排序一起改掉（两处共用一个 ref），
那不是这个弹窗该干的事。

**明确没做**：组合嵌套；组合行倍率；「这个组合该有几件」。

### 十四期：库存流水 —— 「这东西是怎么变少的」（v3.60.18 · P0）

页内**第 5 个 tab**（不新增侧边栏菜单项 ⇒ 版本号是 patch）。

| 面板 | 数据来源 | 回答 |
|---|---|---|
| **库存流水**（`SurvivalFlowPanel.vue`） | 人登记 + **系统代记** | 这东西是怎么变少的 |

🔴 **这个 tab 只「查」，不「登」。** 登记入口长在**物品上**（物品清单每行的
「用掉 / 入库」）—— 用户想「我吃了一罐」时，眼睛盯的是那件物品，
不是流水页。在流水页放开登记，等于逼他先选一次物品（那才是真正的重复填写）。

**① 浮层只有一格需要打字**（`SurvivalFlowDialog.vue`）：

```
物品名 / 单位    从物品带出，只读      —— 已从那件物品点进来，再问一遍才是重复
当前数量         只读                  —— 改的是「变化量」，不是「绝对值」
数量             默认 1、自动聚焦全选   —— 「1 件 / 1 份」是绝大多数情况
原因             留空即可              —— 后端按类别消耗模式自动记
时间             默认「刚刚」           —— 补记才点开 ✎
渠道             系统填 manual         —— 用户不需要知道这个词
```

⚠️ **「用掉几件」与「还剩几件」永不并列。** 并列问两个的后果不是多填一格，
是**静默错账**：两个都填了，系统只能听一个。这里只问前者，
后者由 `当前 − 用掉` **算出来**摆在旁边当预览（防错，不是第二个输入框）。
预览里的减法是**纯展示**：真正的判定（不能为负、不能为 0）在后端，
前端只是把「会变成负数」提前说一声，并禁用确认按钮。

**② 三个刻意的展示取舍**：

| 取舍 | 为什么 |
|---|---|
| **不上涨红跌绿** | 「吃掉」不是亏损、「入库」不是盈利，只是方向不同。方向只用符号区分（`−` / `+`），颜色保持中性（同「盘盈盘亏不套价格语义」） |
| **汇总不给「总消耗 X 件」** | 「3 斤米 + 2 罐罐头」不可通约。按单位分桶列、**桶内才求和** —— 那个合计数看起来最像答案，其实最没有意义 |
| **空态说真话** | 功能上线之前的库存变化**没有留痕**，不补造假的「期初基线」 |

**③ 🔴 「查不出来」有两种，不能合口**（v3.60.18 修）：

| 情形 | 界面 |
|---|---|
| 取到了，一条都没有 | 「这个月还没有流水」 |
| **这次没取到**（迁移没跑 / 接口 500） | 「取不到」，且明说**列表为空不代表没有流水**，并给重试 |

只写前一句的后果：一次 500 被读成「我这月没吃任何东西」——
**把系统的失败记到了用户的账上**。所以 store 有四个互斥态
（`listError` / `summaryLoaded` / `summaryError` / 有数据），
且汇总卡这四态必须挂在**同一条 `v-if` 链**上（拆成两条会同时命中两种，实测过）。

**④ 筛选下拉的选项从实际数据里聚合**，不硬编码一份：
硬编码迟早与后端枚举分叉，而分叉是静默的 —— 下拉里会有一个「选了永远查不到东西」的项。

**⑤ 撤销的话要说全**：确认框写明「会补一条反向流水把账正回来，两条记录都会保留
（不会删除任何东西）」。用户以为在「删记录」时会期待东西消失，实际是多出一条冲销记录。
已撤销的行**不再显示按钮**（让它可点、点完报错，是对用户的一次白跑）。

⚠️ **别处的登记要通知本 tab**：清单上记了一笔之后，父级发的是**刷新信号**
（`flowStore.bumpRefresh()`），不是替它取数 —— 页签有自己的筛选条件，
父级替它取会把筛选悄悄重置掉，而重置是静默的。

## 物件资产：盘的是耐用品，不是钱（v3.60.0，P4-A 一期；v3.60.1 订正净值口径）

它盘的是**会折旧、会报废**的东西（冰箱 / 空调 / 床 / 柜子），
答案的单位是「年」与「元」。与 `/wealth/survival`（消耗物，答案是天）
是两条路径，**判据一句话：纸巾会被用完 → 生存资源；冰箱会被用坏 → 物件资产。**

独立路由 `/wealth/property`（name `wealth-property`），
**不进 WealthHub 的 tab** —— 同 `/wealth/survival` 的处理方式。

四张卡 + 一句「此合计不计入净资产」的说明。**没有结论条** ——

### 三个必须记住的展示口径

**① `null` 不等于 0。**
`current_value === null` 是「算不出来」（缺金额 / 缺日期 / 缺年限），
`¥0.00` 是「真的折完了」的结论 —— 一个该去补数据，一个该考虑换新。
所以表格里 null 显示「—」，**并且旁边能点开看为什么**（`issues` 那几句）；
空壳的破折号比一个说明更难排查。

🔴 别直接调 `formatAmount(value)` —— 它对 null 返回 `0.00`，
正好会把「算不出来」画成「真的折完了」。金额一律走 `formatMoneyOrDash`（先判 null）。

**② 超期只做中性标注。**
「计划用 8 年、已经用了 10 年 2 月」不是一条判好坏的线，它只是两个数并排摆着。
所以「已超期 X 年 X 月」是**灰字**，没有图标、没有红黄绿、不弹窗、不建议更换。

**③ 未填金额恒排最后。**
`sortItemsByAmount` 两个方向都把 `purchase_amount` 为空的排在最后 ——
未填金额不是一个「便宜」的值。若按 0 参与排序，升序时那批
「想不起来多少钱」的物件会挤在最前面，看起来像一堆破铜烂铁。

### 前端只做三件事

1. **不判算法、不折算** —— 年限换算、月折旧、净值、四项合计全部来自服务端；
   前端只摆数。本模块前端**唯一**的年↔月换算在 `propertyFormat.yearsToMonths` /
   `monthsToYears`，别处不许再写 `/ 12` 或 `* 12`。
2. **口径文案来自 `/meta/`** —— 状态/状况词表、每个数的公式与要点、那一句
   「不计入净资产」都从后端下发，前端不硬编码。
3. **金额走 `format.ts`、脱敏走 `privacy.ts`** —— 不新写第三份。

### 排序与筛选都在前端

后端刻意**不开 `?ordering=`**：一开，`current_value`（派生值、不落库）
就会被逼着落库。筛选也在前端做 —— 家当量级小，且四卡点击筛选要跟列表**瞬时**联动。
（后端那几个 query 参数仍然可用，只是界面不走它们。）

### 两个易错点

- **`DecimalField` 在响应里是字符串**：直接算数或比大小会得出荒谬结论
  （`'10' < '9'`）。`propertyFormat.toNumberOrNull` 统一收口。
- **`el-input-number` 清空后给 `null`**：直接透传会让后端 `IntegerField` 400。
  排序那格归 0；年限 / 金额那两格 `null` 是**有语义**的（= 不填），保持原样。

### 净值那个 ¥0 有三种来路（v3.60.1 起）

| 显示 | 含义 | 判断依据 |
|---|---|---|
| 「—」（可点开看原因） | 算不出来（缺金额 / 日期 / 年限 / 购买日在未来） | `current_value === null` + `issues` |
| 「（已折完）」 | 计划年限真的用完了，该考虑换新 | `zero_reason === 'depreciated'` |
| 「（损坏归 0）」 | 还没到期就坏了，该修或者该扔 | `zero_reason === 'broken'` |

🔴 **判断依据是后端下发的 `zero_reason`，不是 `row.condition === 'broken'`。**
前端原先按「值等于 0」判、一律写成「已折完」—— 口径一改（损坏 ⇒ 按 0 计），
坏掉的物件就被说成「用够了」，两句话看着都通顺，**错得毫无声响**。
处置不是在前端补一个分支（那是第二份口径，下次改口径必漏），
而是把这套判断收回后端：`propertyFormat.formatZeroReason` **只查表**。

### 净值合计上那句「N 件损坏按 0 计」

勾一下「损坏」会让在用净值合计掉一截，而「计入件数」纹丝不动 ——
正是那种「两个数对不上、还没人会去查」的形态。后端的 `broken_count`
经 `formatExcludedHint` 拼进卡③副行，措辞是「**按 0 计**」而**不是**「未计入」：
那些件是计入的，只是金额为 0；写成「未计入」会把它跟「缺数据」混成一类，
而两者该采取的行动相反（一个不用补，一个要去补）。

### 弹窗里的试算

`PropertyFormDialog.vue` 实时把「已用 / 计划 / 月折旧 / 净值」摆出来：

```
空调  计划用 8 年 · 已用 10 年 2 月 · 已超期 2 年 2 月
月折旧 ¥312.50 · 当前净值 ¥0（已折完）

眼镜  计划用 3 年 · 已用 1 年 5 月 · 状况标为「损坏」
月折旧 ¥7.97 · 当前净值 ¥0（损坏归 0）     ← 勾上「损坏」当场就是这一行
```

⚠️ 走**后端同一个接口**（`POST /api/wealth/property/items/preview/`，输入防抖 400ms），
绝不在这里自己除一遍 —— 那份公式与 `property_calc` 迟早分叉，而**分叉是静默的**。
⚠️ 试算是**护栏、不是闸门**：它自己失败只收起提示，绝不阻断保存。
