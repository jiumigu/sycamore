# Treasure — 好恶物档案馆

> 文档对齐 v3.64.5 ｜ 最后核对 2026-10-29

「好恶物双面档案」：记录你**亲自验证过**的好东西，和踩过的坑。
同一张表按 `record_type` 分成两副面孔 —— 好物写「为什么好 / 在哪能找到」，歹物写「踩坑原因 / 实际后果」。

## Models

| Model | Table | 用途 |
|-------|-------|------|
| GoodThing | treasure_good_thing | 双面档案（`record_type` 好 / 歹） |

### 两根轴，不是一个枚举（v3.60.32 拆分）

| 轴 | 字段 | 取值 | 谁用它 |
|---|---|---|---|
| 记录对象 | `subject_kind` | 实物 / 方法 | **决定显示哪些字段** |
| 类别 | `category` | 吃 / 穿 / 用 / 店 / 地方 / 服务 | 只有**实物**才有 |
| 方法归类 | `method_group` | 生活 / 工作 / 学习 / 工具 / 人际 / 其他（可留空） | 只有**方法**才有 |

🔴 拆分原因：旧版把「方法」放在 `category` 里，但六个取值中
**吃/穿/用/店/地方 回答「这东西干嘛用的」，方法回答「这东西是不是实物」** ——
两句话不同质。一个互斥枚举里混进不同质成员，**它必然变成兜底桶**
（实测：23 条档案里 17 条 = 74% 是「方法」，里面装着人、公众号、课程、App 价格）。

由此 `subject_kind` 决定字段分流：

| `subject_kind` | 独有的字段 |
|---|---|
| `实物` | `category`、`still_available`、`where_to_find` |
| `方法` | `method_group` |

⇒ 「在哪能找到 / 还能找到吗」不再对着方法型空着
（那 17 条**不是用户懒得填，是问题没有答案**）。

### 字段随 `record_type` 分化

| `record_type` | 用到的字段 |
|---|---|
| `好` | `why_good`、`still_available`、`where_to_find` |
| `歹` | `avoid_reason`（踩坑原因）、`consequence`（实际后果） |

两侧都有的字段：`name` / `scene` / `tags`，以及两个关联外键（见下）。

### 关联两个实物池（v3.60.32）

| 字段 | 指向 | 约束 |
|---|---|---|
| `property` | `wealth_property`（物件资产） | `SET_NULL` · **唯一** · 与另一个互斥 |
| `survival_item` | `wealth_survival_item`（物品清单） | `SET_NULL` · **唯一** · 与另一个互斥 |

🔴 **FK 用 `SET_NULL` 不用 `CASCADE`**：物件被删掉之后，那条评价的文字
（「这个型号选错了，吵」）仍有独立价值，不该跟着一起消失。

⚠️ 两个「唯一 + 互斥」**不能只靠 `Meta.constraints`**：可空列上的
`UniqueConstraint` 在 MySQL 里允许多行 NULL，而 DRF 对 `Meta.constraints`
**静默放过**（它只认序列化器字段级校验）⇒ 必须在 `serializers.validate()` 里
手写 1:1 唯一检查与两 FK 互斥检查，否则会得到一个 500 或一条没有报错的脏数据。

## 口径单一真源

`constants.py` 是**唯一**存放处，前端不写第二份 label：

- `CATEGORY_LABELS_BY_TYPE` —— 🔴 **key 好/歹共用，label 两侧各一套**。
  好物侧「🏪 好店」、歹物侧「🏪 坑店」。key 共用是为了**避免值重写迁移**
  （存量歹物已有 `吃`/`用` 等值，拆 key 就得批量改值，漏一条映射就是静默错值）。
  ⚠️ label **自带褒贬**，所以 `get_category_display()` 永远分不了侧 ——
  界面一律走 `category_label(record_type, key)`。
- `SUBJECT_KIND_CHOICES` / `SUBJECT_KIND_OPTIONS` —— 必须**同源**
  （options 从 choices 派生）。各写一份的下场是「下拉里有、模型不认」。
- `suggest_category_for_property()` —— 按物件类别名**猜**预填类别。
  ⚠️ 只用作表单预填（用户看得见、能改），**不参与任何校验、不参与写入决策**；
  猜不出返回空串，**不硬塞一个「看着合理」的值**。

## 徽标回流

`badges.py` · `attach_badges(rows, kind)` 给物件资产 / 物品清单的列表行
**就地**补三个只读字段：

| 键 | 含义 |
|---|---|
| `treasure_badge` | `None` / `'好'` / `'歹'` |
| `treasure_record_id` | 已有评价时那条档案 id（点徽标去**同一条**补理由） |
| `treasure_suggest_category` | 快记浮层类别下拉的预填值 |

三条纪律（都在 `badges.py` 文档串里）：

1. **真源唯一在本 app**。两个实物池**不加**「是不是好东西」字段、**不缓存**徽标 ——
   缓存一分就会在改档案后漂移，而漂移是静默的。
2. **不给前端「拉全量档案本地建 map」的口子**。档案会增长，全量拉取一旦被分页
   截断就是**静默缺标识** —— 看起来像「本来就没人评过」。
3. ⚠️ **`badge is None` = 从没评过 ⇒ 界面什么都不显示**，
   不渲染成灰色的「无」。「没评过」和「评过了、结论是没有」要采取的行动不同。

⚠️ 一次 SQL 查完**一页**（不是逐行查）：列表是 78 / 58 件的量级，N+1 在小数据量下
看不出来，等数据涨了才会慢。

## 出口：「值得留」（v3.62.12，**不在本模块存**）

档案馆页面上每条记录有一个「**值得留**」标记（列表卡片上、详情弹窗底部）。
标上它，这条评价就进入「作品」页的待提炼，等着被收成一件东西
（一份清单、一个方法、一段记录都算）。

🔴 **本模块不为它加任何字段。** 那个勾的真源是 `works.WorkCapture` ——
档案只是它的**第七个入口**（另外六个是里程碑 / 收件箱 / 读书 / 日记 / 摘录 /
AI 问答），**同一个勾，同一个含义**。

给 `GoodThing` 加 `is_worth_keeping` 会同时坏两件事：

1. 一个勾抄成两份，两份对不上**不报错**；
2. 它成了**第二个录入口** —— 收口台之外还有一处能标记，收口台就不再是收口台。

⚠️ 打勾时写下的：**标题 = `name`**、**摘要 = `why_good`（好物）/ `avoid_reason`（歹物）**，
与 `has_reason()` 同一套判断（「这条有没有理由」正是「这条有没有内容可留」）。
前端接法见 `frontend/src/modules/treasure/views/TreasureHub.vue`
—— `useWorkKeep('treasure')` 在**页面**调一次，卡片与详情弹窗共用同一个实例
（各调一次就各持一份 rows，会出现「卡片已勾、详情未勾」且不报错）。

## 三把正交的尺子（最容易出错处）

| 尺子 | 在哪 | 回答 | 性质 |
|---|---|---|---|
| `status` | 物件资产 | 我还要不要它 | 主观意愿 |
| `condition` | 物件资产 | 它现在好不好使 | **客观** |
| `record_type` | 本 app | 我认为它值不值 | **主观** |

**并列显示、互不推导。👎 ≠ 该报废，👍 ≠ 状况良好。**
冰箱可以「状况=正常」却 👎（型号选错，用着别扭）；
空调可以「状况=坏了」却仍是 👍（用了 12 年，值了）。

🔴 **评价不参与任何计算** —— 不进净值、不进生存天数、不进任何统计口径。

## API Endpoints

前缀 `/api/treasure/`（⚠️ 路由名是 `things` 不是 `good-things`）

| 方法 | 端点 | 用途 |
|------|------|------|
| GET/POST | `/things/` | 列表 / 创建。筛选：`?record_type=&subject_kind=&category=&pending_reason=1` |
| GET/PUT/DELETE | `/things/<id>/` | 详情 / 更新 / 删除 |
| GET | `/things/meta/` | 口径下发：`subject_kind_options` / `method_group_options` / `categories_by_type` / `record_type_options` |
| GET | `/things/link_candidates/?search=` | 档案侧「输入即搜实物」的候选 |

🔴 **列表不分页**（`pagination_class = None`）⇒ 返回**裸数组**。
若哪天要加分页，消费侧必须同步改 —— 否则按数组取用会得到「**假 0**」。

🔴 `link_candidates` 返回的是 `{rows, total, limit}`（**不是**裸数组）——
这是**有意的**：它有取数上限（`LINK_CANDIDATE_LIMIT = 20`），
**有上限就必须把上限说出来**，前端要显示「还有 N 条没显示」。
（与被分页包住的裸数组那种「假 0」是**两回事**。）

`linked_facts`（关联实物的派生事实）**只在 `retrieve` 下发**，
列表里对每条都算一次折旧就是 N+1。取值时**不重算** ——
物件侧走 `property_service.get_item()`，与物件资产页同一把尺子。

## 边界

- `user_id` 字段存在但**只是预留**，视图不读写、不做多用户隔离（单用户系统）。
- `rating` 列**保留、数据不动**，但前端已撤下 —— 存量 23/23 全是默认的 5 分，
  每张卡片挂「5 分」是零信息量，且与 👍/👎 + 理由这个维度重复。
- 侧边栏入口在「精神滋养」分组的「**好恶物档案馆**」（`/treasure`）。
  ⚠️ 曾叫「好东西」，与页面标题不一致 ⇒ v3.60.32 统一。
- **不做名称自动匹配写入**。物件叫「小米扫地机」、档案里写「扫地机器人」，
  自动匹配会把两条不相干的东西绑在一起，而界面上看起来完全正常。
  只做「输入即搜 + 用户显式点选」。
